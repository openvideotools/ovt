# Fuzzing the header parsers (WI-1.129)

The fuzz harness itself (`ovt_add_fuzz_target`, the regression replay, the `fuzz-smoke` CI job and the nightly
run) comes from WI-0.557 and WI-0.033 (chapter 14 §14.7). This page covers the header-parser targets of WI-1.129
(chapter 7): how they are built, where their seeds come from, and the coverage report that acceptance test 2 asks
for.

## Targets

| Target | Input | What runs |
|---|---|---|
| `fuzz_h264_units` | one H.264 NAL unit (header and emulation prevention bytes, no start code) | every parser that accepts the `nal_unit_type`, as `core/src/index/h264_units.cpp` dispatches it, against each canned context; then `parse_parameter_set()` (the `avcC` path) |
| `fuzz_h265_units` | one H.265 NAL unit | the same for H.265: slice segment header, activation, RPS in use and entry-point substreams; VPS / SPS / PPS into `ActiveSets`; prefix / suffix SEI; then `parse_parameter_set()` (the `hvcC` path) |
| `fuzz_av1_obus` | one OBU (header, optional `obu_size`, payload) | sequence header, temporal delimiter, frame header and redundant frame header (followed by the §7.20 update or the §7.21 loading process), `frame_obu()`, tile group, metadata, tile list, padding; then `parse_parameter_set()` (the `av1C` path) |
| `fuzz_index_builder` | framing selector byte + an Annex B or OBU stream | the StreamIndex builder end to end (WI-1.121; WI-1.129 reuses it and adds the stream seeds) |

A **context** is the parameter sets of one seed stream (`core/tests/fuzz/fuzz_unit_contexts.inc`, generated): for
H.264 the first SPS and PPS; for H.265 the first VPS, SPS and PPS plus the start of the first slice segment, which a
dependent slice segment copies; for AV1 the first sequence header and the header of the first frame, which the
reference frame update process saves into all eight slots. Each target has 10 contexts, one per seed stream. Every
run copies a context that was built once per process, so no state carries over from one input to the next.

The checks in `ovt_fuzz::drive()` (`core/tests/fuzz/fuzz_units_common.h`) are:

- Only `ovt::ParseError` escapes a parser. Any other exception, a crash or a sanitizer report is a finding.
- One pass over all contexts finishes in under one second. This catches quadratic loops.
- One context runs twice more, picked as the input size modulo 10 so that most mutations keep it. With recording on,
  it must give the same tree fingerprint. With recording off, it must succeed or fail alike, with the same
  `ParseError` code, and on success end at the same bit.

The trees are compared by fingerprint, not by JSON. `to_json()` costs about ten times the parse in the sanitizer
build and would starve the 60 s smoke run. JSON output is already covered by the older per-parser targets.

## Seeds

```sh
python3 -I tools/fuzz_seed.py --make-streams /tmp/fuzz-streams        # needs ffmpeg with x264, x265, aom, svt-av1, rav1e
for t in h264_units h265_units av1_obus index_builder; do
  python3 -I tools/fuzz_seed.py --target "$t" --streams /tmp/fuzz-streams
done
python3 -I tools/fuzz_seed.py --contexts --streams /tmp/fuzz-streams   # rewrites fuzz_unit_contexts.inc
```

`STREAMS` in `tools/fuzz_seed.py` holds the recipes for 10 small streams per codec (96×64 or 70×46, 8 to 12
frames, FFmpeg `testsrc2`). They vary the features the header parsers branch on:

- H.264: High with B-pyramid and weighted prediction, Baseline, MBAFF, fake interlace with `pic_struct`, High 4:2:2
  10-bit with JVT scaling matrices, 4:4:4 lossless, CBR NAL HRD with filler, slices with AUD and intra refresh,
  CAVLC with open GOP, and PQ 10-bit cropped with MDCV/CLL SEI.
- H.265: B-frames, Main 10 HDR10 SEI, 4:4:4 with transform skip, WPP with slices, HRD with AUD, MD5 hash with
  temporal layers, scaling lists with AMP, open-GOP CRA with EOS, weighted prediction, and 4:2:2 10-bit
  intra-only cropped.
- AV1: libaom 4:2:0, 10-bit screen content with delta q, 4:4:4 with restoration, monochrome with 128×128
  superblocks, film grain, 2×2 tiles error-resilient, lossless, SVT-AV1, rav1e, and PQ without order hints.

Every byte is generated by OVT tools. No third-party test vector is committed: §14.7.2 forbids seeds cut from the ITU-T
or AOM conformance vectors.

The per-unit seeds keep up to three units of each type per stream, deduplicated. H.26x slices are cut to 256 bytes,
because the header parsers stop at `slice_data()`. The seeds also include the hand-made units of the older targets
that no encoder writes: MVC/SVC subset SPS, prefix NAL, SPS extension, rare SEI payloads, AV1 metadata and tile
lists. The `index_builder` seeds are the selector byte plus the first 64 KiB of every stream. Encoder output changes
between encoder versions, so `--check` compares against the committed files only when they were made with the same
encoders.

## Coverage report (acceptance test 2)

```sh
# 1. Sanitizer fuzz build (the linux-x64-fuzz preset; any Clang with libFuzzer)
cmake --preset linux-x64-fuzz && cmake --build --preset linux-x64-fuzz \
  --target ovt_fuzz_h264_units ovt_fuzz_h265_units ovt_fuzz_av1_obus ovt_fuzz_index_builder
# 2. Ten minutes per target, in parallel, each growing its own corpus directory
for t in h264_units h265_units av1_obus index_builder; do
  mkdir -p grown/$t
  build/linux-x64-fuzz/fuzz/ovt_fuzz_$t -max_total_time=600 -max_len=1048576 -timeout=10 -rss_limit_mb=2048 \
    grown/$t core/tests/fuzz/corpus/$t &
done; wait
# 3. Coverage build (Clang, -DOVT_COVERAGE=ON, Debug, no sanitizers) with the *_regress binaries, then replay
tools/fuzz_coverage.sh build/cov out/cov \
  h264_ps h264_sei h264_slice h264_index h265_ps h265_sei h265_slice syntax_av1 syntax_av1_frame_header \
  syntax_av1_frame_header2 av1_frame_boundary user_data stream_api lazy_rbsp unit_scan \
  h264_units:grown/h264_units h265_units:grown/h265_units av1_obus:grown/av1_obus index_builder:grown/index_builder
```

Step 3 replays the committed seeds and regressions of every target that reaches `core/src/syntax/`, plus the
corpora grown in step 2. It reports `llvm-cov` line coverage of `core/src/syntax/**`. The "mismatched data"
warning comes from `LLVMFuzzerTestOneInput`, which is defined in every target; it does not affect the syntax files.
